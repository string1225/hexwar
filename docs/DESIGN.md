# 方案评估与实现

## 结论

这一玩法适合采用原生 JavaScript + Canvas 2D。完整地图最大 195 格，同轮允许连续下达多条指令，计算和渲染成本低，无需引入大型游戏引擎。共享 Canvas UI 可以让浏览器和微信小游戏使用相同的规则和交互，降低双端行为偏差。

当前实现完整单人战役；浏览器用于快速试玩和迭代，微信构建用于开发者工具 / 真机接入。战斗无需联网；139 服务器提供可选的微信登录与手动云存档。游戏和后端运行时无第三方 npm 依赖，开发工具使用 esbuild 与 miniprogram-ci。渲染仅在交互、窗口变化或状态变化时进行，没有空转的持续帧循环。

## 明确的规则选择

当前 1.5.0 的规则如下，便于测试和继续调整：

| 项目 | 当前实现 | 原因 |
| --- | --- | --- |
| 地图 | 六边形外形 37 / 91 / 169 格，长方形外形 35 / 99 / 195 格；内部随机移除约 8%–12% 地块 | 地块仍为六边形；外边界不挖空，移除时检查整图连通；空洞不可通行 |
| 敌军数 | 1–5 个 | 让小地图也有单挑与混战选择 |
| 开局 | 每方 18 兵，占 1 格；先随机一点，再按最短路径距离分散选点并随机分配势力 | 出生点至少三个相邻格，两出生点不相邻；随机种子可复现 |
| 敌军智能 | 初级随机扩张、中级稳健扩张、高级协同进攻 | 三档规则相同，策略区别；不读取玩家计划 |
| 回合 | 各方基于同一快照规划，全部锁定后同步结算 | 规划阶段不改变兵力或领地 |
| 移动 | 只能调兵到六个相邻格之一 | 保留六边形策略的局部决策 |
| 驻守 | 至少保留 1 兵 | 避免空领地所有权歧义 |
| 概率 | 多方 B_i^k / ΣB_j^k，两方退化为 1 / (1 + (D/A)^k)，k = ln(19)/ln(3) | 1:1 为 50%，3:1 为 95%；只由兵力比决定 |
| 伤亡 | 败方全灭；胜方损失以 ceil(败方总兵力/2) 为基准，60% 不变、各 20% 上下浮动；胜方至少剩 1 | 浮动量 max(1, round(基准 × 20%))；双方相同规则 |
| 增长 | 完整一轮后，每个占领格 +1，中立格不长兵 | 鼓励扩张，避免中立兵力随等待无限上涨 |
| 持续行军 | 每对相邻友军一条指令，每轮 1–99 兵；同起点可多方向 | 本回合指令先占额度，每回合多方向只按比例共享剩余兵力；保留 1 兵 |
| 指令结算 | 所有出征先扣除；同边对向交战，胜方继续；同格同势力合兵，再统一战斗；整轮后增长 | 共享出兵前快照，新到的兵不能再次出发；循环线路不增兵 |
| 胜利 | 玩家成为唯一存活势力 | 不要求清理无关中立地块 |
| 失败 | 整轮全部结果落定后玩家没有任何格子 | 不提前取消已在途中、可能攻占新领地的部队 |
| 存档 | 每条指令后本地保存，带版本和结构校验 | 中断后恢复；损坏存档安全回退 |

## 引擎与平台分层

`createGame(config)` 建立带随机种子的状态。`applyCommand(state, command)` 校验指令、复制并返回新状态，原状态保持不变。`MARCH` 只写入统一的 `orders` 计划，以 `frequency: once / repeat` 区分本回合和每回合执行；`CANCEL_MARCH` 撤销计划，各势力的 `END_TURN` 锁定计划，最后一个存活势力锁定时原子结算全轮。旧 `MOVE`、`SET_ROUTE`、`REMOVE_ROUTE` 入口也转为计划语义。相同起点和目标只有一条指令，编辑不会产生第二条指令，也不产生执行优先级。坐标使用 axial q/r，邻居与距离独立于渲染。

随机算法状态保存在游戏状态中，战斗、开局和 AI 决策可复现。每轮只推进一次主随机流，各条边和各个格子按位置与阶段派生独立随机流，交换指令录入顺序或地图遍历顺序不会改变战果。地图生成与 AI 策略分别在 `map.js`、`ai.js` 中实现。初级随机邻接移动；中级评估可行进攻、预留驻防、沿己方路径向前线补给；高级用同势力的已规划来军和未行动邻军协调合兵，并提高受威胁前线的补给优先级。补给只沿己方领地向前线距离递减的方向移动，尊重空洞且不循环。AI 每回合每个原有领地最多出兵一次，不使用对手指令；双方使用相同的兵力、增长、战斗和胜负规则。

界面不直接修改游戏兵力。所有游戏变更通过规则指令，界面仅保存选择、派遣数量、缩放等展示状态。平台适配只负责 Canvas、图片、输入、窗口、安全区、存储和生命周期。

AI 在短暂间隔后逐势力完成规划，期间地图兵力和随机状态不变，AI 不读取玩家计划。最后一方锁定后统一结算；重开战役会使旧任务失效。存档 v6 保存地图配置、智能档位、所有已锁定和正在编辑的 `orders` 与 `aiPending`。v1–v5 完整地图保持原样，补入 hexagon / holes=false / standard；v4–v5 保留中途 AI 规划状态。v1 / v2 运输路线迁移成持续计划；v1–v4 超额一次计划按比例缩减到预算；v5 与新版超额计划拒绝。v1–v3 存档若停在旧 AI 行动中，保留已执行后的地图并回到玩家规划，避免重放。存档始终先写本机；打开默认存档页不联网，可选云端入口使用静默读取，静默读取或写入失败不显示错误、不覆盖本机进度。

界面以战场为主，桌面移除左侧大面板，顶部压成两行，底部简报缩为一行。手机指令区固定 184px，选择、保存、修改、撤销指令时地图与操作按钮不移动。设定后保留当前目标、数量和频率；未修改的更新按钮置灰，数量或类型改变才点亮，保存后再次置灰；下次点格直接选中（敌方与中立格只查看），不沿用旧起点判断方向；「本回合指令」统一列出一次性及持续计划。存档仍在右上角独立弹窗。选中格没有发光阴影；攻占成功不弹提示。胜率只用于内部结算，行军面板、指令列表和玩法说明均不显示数值或公式。

## 性能与边界

- 最多 6 个势力、195 个地块（空洞前）；地图与路线遍历均为小规模计算。
- Canvas 设备像素比上限 3，按需重绘，避免静态战场持续耗电。
- 一格最大 9999 兵；所有指令验证整数、所属势力、距离和兵力。
- 全轮以起始兵力快照分配出征，不使用刚收到的兵力。友军容量含同时出发腾出的空间，先为本回合来军分配容量，再给每回合来军分配；同级超额按比例缩减并留在原地，容量减少会向上游传播直至收敛；战斗后驻军上限为 9999。
- 保存最多 60 条简报，避免长期对局无界增长。
- 微信版的云存档按微信账号隔离，手动备份 / 读取；本地游戏独立运行。当前存档可被用户自行修改，不承担联网反作弊职责，详见部署说明。

## 出兵额度与优先级

`availableTroops` 为引擎与 UI 共用的额度计算：原兵力 − 1 驻军 − 其他方向本回合预约量。编辑当前方向时计回旧指令额度，每回合计划不预占本回合额度，收到的兵也不能提前使用。设置、修改与类型转换都通过引擎校验，UI 的加减和快捷比例按钮同样受限，额度为 0 时禁用一次性派遣。结算先满足本回合计划，每回合指令按原请求比例分享余兵，无余兵时保留指令但本轮不移动。

## 途中交战与合兵

A→B 和 B→A 的敌对部队先以出征数量交战，双方相同的胜率与随机战损规则，只有胜方幸存者继续原方向。道路胜负与攻城使用不同随机流。各目标格再把驻军（原兵力减出征）与同势力援军合并，所有参战势力一次加权抽签，胜方只计算一次对败方总兵力的战损。全部格子结果先收集再写回，最后处理淘汰和胜负。

## 后续 2–4 人联机

回合制适合**服务端权威状态 + WebSocket 指令广播**，无需先做复杂实时动作同步。

1. 增加房间 / 邀请 / 2–4 人座位、身份和准备状态；按座位配置人类与 AI。移除当前引擎中「玩家 0 淘汰即结束单人战役」的结束规则，替换为多人淘汰 / 观战策略。
2. 服务端维护规则状态、随机数、当前回合和指令序号；客户端仅提交意图。服务端使用同一规则模块验证身份、轮次、相邻性和兵力。
3. 每条指令携带 roomId、actor、expectedRevision、唯一 commandId。拒绝越权 / 旧版本指令，重复提交保持幂等。
4. 广播新状态或事件；记录初始种子及指令序列，支持回放和纠纷定位。
5. 加入超时跳过、掉线重连、快照恢复和断线托管，再处理微信登录和好友邀请。
6. 对未来未发生的战斗，随机状态留在服务器，避免客户端提前推演随机结果。

这部分需要真实 AppID、后端环境和多人网络验收，尚未在当前单人版实现。现有确定性命令边界可复用，但不能直接把本地存档当作可信的线上状态。

## 上线验收

已实现的首版不等于已发布到微信。正式交付上线前应使用目标账号在微信开发者工具与 iOS / Android 真机上完成：触屏与安全区、小屏大地图、切后台续局、长局性能、存储不可用、失败与胜利、包体与资源加载等验收，并完成对应的微信平台发布流程。

### 能力与边界

- 代码混淆：提高分析、复制和修改 JavaScript 的成本，等级 1–3 会影响体积及性能。
- 代码水印：辅助识别代码来源与归属。当前微信版 JS 打包成单一 `game.js`，约 43 KB（调研时的 1.4.0 产物），适合作为加固目标。
- 概述提到代码锁和部分对抗外挂能力，但提供的配置示例主要覆盖混淆与水印。包类型声明另有 `plugin_protect`，其开启条件、账号权限及运行行为未实测，不能据此宣称已经实现反外挂。
- 当前游戏在本机结算兵力和战斗，本机存档也由客户端管理。加固可增加篡改成本，无法建立可信服务器战局；未来竞技排名、奖励或多人模式仍应由服务端校验指令并结算。
- 本项目的源代码许可证为 MIT；构建产物的加固不会改变已有源码许可。

### 凭据与排错

本机 Node 24.13.0 满足文档最低 17.5.0 要求。需要为该 AppID 生成专用 RSA PEM 密钥对，由管理员在微信后台“开发支持 → 研发工具箱 → 密钥管理”登记公钥；`id_rsa.conf` 包含 AppID 和私钥，必须保存在小游戏工程之外。现有“代码上传”私钥不能自动视为已登记的加固密钥。示例中的密钥不可作为实际凭据使用。

每个版本保留原始产物、加固产物、原始及加固 sourcemap、配置和哈希，便于回滚与错误映射；含源码的 sourcemap 作为开发资料保存，不放在公开 Web 目录。文档说明可能有每日调用限制、时间戳与验签错误、较大文件超时，以及未改动文件 24 小时内复用结果；具体账号额度和可用性未验证。
